# Постоянное хранилище на Railway (фикс сброса фото/базы при передеплое)

## Проблема

Railway пересобирает контейнер с нуля при каждом деплое. Всё, что лежит
внутри файлов проекта (`server/data/db.json`, `server/uploads/*`), физически
живёт внутри образа контейнера — новый деплой стирает и то, и другое.
Vercel (фронтенд) тут ни при чём — он и так статика без собственных данных,
проблема только в бэкенде на Railway.

## Решение — Railway Volume

Volume — это отдельный постоянный диск, который подключается к контейнеру
по фиксированному пути и переживает передеплои, в отличие от самого
контейнера.

### 1. Создать Volume в Railway

1. Откройте ваш сервис (бэкенд) в Railway → вкладка **Settings**
2. Найдите раздел **Volumes** → **New Volume**
3. Mount path укажите, например: `/data`
4. Размер — 1 GB для старта более чем достаточно, можно увеличить позже

### 2. Прописать переменные окружения сервиса

В Railway → ваш сервис → **Variables** добавьте:

```
DATA_DIR=/data
UPLOADS_DIR=/data/uploads
```

Код уже готов к этому — `server/src/db.js` и `server/src/routes/cars.js`
теперь читают эти переменные (если не заданы — по умолчанию работает как
раньше, локально, внутри папки проекта, так что для локальной разработки
ничего менять не нужно).

### 3. Задеплоить

После деплоя с этими двумя переменными и подключённым Volume:
- `db.json` будет создан по пути `/data/db.json`
- Фото будут сохраняться в `/data/uploads/`

Оба пути живут на Volume, а не внутри контейнера — следующий передеплой их
не тронет.

### Как проверить, что всё сработало

1. Задеплойте, загрузите тестовое фото через приложение
2. Сделайте любой новый деплой (например, пустой коммит `git commit --allow-empty -m test && git push`)
3. Откройте приложение снова — тестовое фото должно остаться на месте

Если фото пропало — значит Volume не подключён или переменные окружения не
попали в новый деплой (проверьте вкладку Variables ещё раз).

## Что дальше (если проект вырастет)

Volume отлично работает для одного инстанса бэкенда. Если в будущем
понадобится несколько реплик сервера (горизонтальное масштабирование) —
Volume общим для всех реплик не станет, и тогда правильный путь:

- **Фото** → объектное хранилище (Cloudflare R2, AWS S3, Backblaze B2) —
  доступно из любого инстанса одновременно
- **База** → управляемая БД (Railway Postgres addon, Supabase) вместо
  JSON-файла — тоже общая для всех реплик и надёжнее при конкурентной записи

Для текущего масштаба (один бэкенд-сервис) Volume — правильное и полностью
достаточное решение, переезжать на S3/Postgres имеет смысл только когда
реально понадобится больше одного инстанса сервера.
